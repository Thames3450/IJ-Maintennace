# รายงานตรวจ IJ Maintenance — v13.3 → v13.5

ตรวจจาก ZIP ที่ได้รับ โดยอ่านโค้ด React, ส่วนบันทึกข้อมูล, KPI, ไฟล์ SQL อ้างอิง, CSS และขั้นตอน Build แล้วแก้ไขชุดใช้งานหลักใน v13.5

## ข้อสรุป

โครงสร้าง React + Vite + Supabase สามารถพัฒนาต่อได้ ปัญหาหลักอยู่ที่ส่วนควบคุมร่วมของหน้าจอ การแยกสิ่งที่พบ/งานที่จะทำ/สิ่งที่ทำจริง และการแจ้งผลบันทึก เมื่อส่วนเหล่านี้ไม่ชัด ผู้ใช้จึงต้องเดาว่าควรไปหน้าไหนและสถานะที่เห็นหมายถึงอะไร

แนวทางใช้งานที่ปรับแล้ว:

**ตรวจสภาพ → พบปัญหา → กำหนดวิธีแก้ไข → บันทึกสิ่งที่ทำจริง → ตรวจยืนยัน → ปิดงาน**

การตรวจสภาพเป็นบันทึกสิ่งที่พบ ไม่ได้หมายความว่าซ่อมแล้ว ส่วน TPM/PM เป็นงานตามแผนที่ต้องเริ่มงานและบันทึกผลจริง

## ขอบเขตการทดสอบ

- ทดสอบตรรกะด้วย `npm test` รวม 9 กรณี
- ทดสอบ Chromium ผ่านหน้าจอจริง โดยจำลอง Supabase API รวม 20 กรณี ครอบคลุม 14 หน้า
- ทดสอบ Desktop 1280px และมือถือจำลอง 390px รวมทั้งแตะเลือกตัวเลือก
- ครอบคลุม Normal/Abnormal, รูป, ค่า Numeric=0, บันทึกล้มเหลว, บันทึกซ้ำหลังผิดพลาด, แถวอัปเดตว่าง, ประวัติคำตอบสลับลำดับ, งาน Partial, ปิด Defect, KPI Settings และ PM วันนี้
- มีผลละเอียดใน `browser-test-results.json`; ภาพตัวอย่างใช้ข้อมูลทดสอบใน `screenshots/`
- Production build ผ่าน และแนบ `dist/` ที่สร้างจากโค้ดชุดนี้
- ตรวจอ่านฐานจริงแบบ read-only พบว่าตาราง Template และ Items เข้าถึงได้ โดยมี 1 Template และ 12 Items ในขณะตรวจ; ไม่ได้เขียนข้อมูลทดสอบลงฐานจริง

**Dropdown ไม่ปิดที่ผู้ใช้เคยพบ:** ใน v13.3 ไม่พบอาการนี้ซ้ำใน Chromium ภายใต้ข้อมูลจำลอง แต่พบข้อจำกัดของตำแหน่ง/การปิดตัวเลือกในโค้ด จึงปรับ component ร่วมและทดสอบการปิดทั้งคลิกและแตะใน v13.5 ผลทดสอบมือถือจำลองไม่ใช่การรับรอง Safari/iPhone จริง

## ประเด็นที่ยังต้องตรวจในระบบใช้งานจริง

1. **สิทธิ์และ Trigger จริง:** SQL ใน ZIP เป็นบางส่วนและบางไฟล์มีเพียงคำอธิบายว่าเคยติดตั้งแล้ว จึงยืนยันการสร้างฐานใหม่จาก ZIP เพียงอย่างเดียวไม่ได้ ไม่มีการเปลี่ยน RLS/Trigger หรือรัน SQL ในฐานจริงระหว่างงานนี้
2. **หลายคำสั่งบันทึกยังไม่เป็น Transaction:** เพิ่มการลองใหม่โดยใช้ ID เดิม และการล้างข้อมูล Inspection ที่บันทึกค้างแล้ว แต่หากเครือข่ายขาดและคำสั่งล้างข้อมูลถูกปฏิเสธ ต้องตรวจประวัติก่อนส่งซ้ำ ควรพัฒนาการบันทึกด้วย Transaction RPC ในงานถัดไป
3. **การเชื่อม PM Schedule:** ต้องตรวจ Trigger/ความสัมพันธ์ในฐานจริงว่า TPM จาก PM Due ทำให้รายการ PM Schedule ปิดถูกตัวหรือไม่ โค้ดชุดนี้ยังไม่มี source_pm_schedule_id จึงไม่ได้เดารายการ PM เพื่อปิดอัตโนมัติ
4. **ฐานของ KPI:** สูตรปัจจุบันใช้วันปฏิทิน × ชั่วโมงต่อวัน และนับ repair_reports เป็นเหตุการณ์ซ่อม ไม่ใช่ตารางผลิตจริง ส่วน days_per_week ไม่ได้ถูกใช้ในสูตรหลัก ควรยืนยันเกณฑ์กับข้อมูลเดินเครื่องก่อนใช้เป็น KPI มาตรฐาน
5. **โหมด No Login:** คงรูปแบบเดิมไว้ ทุกคนใช้ operator กลาง จึงไม่สามารถพิสูจน์ตัวผู้กดบันทึกจากบัญชี Login ได้ ถึงแม้งานจะระบุผู้รับผิดชอบได้ โหมดนี้ไม่ใช่ระบบกำหนดสิทธิ์รายบุคคล
6. **รูป:** ทดสอบกระบวนการอัปโหลดกับ API จำลองแล้ว แต่ยังต้องลองภาพจากมือถือจริงและสิทธิ์ Storage จริง หากรูปบางรูปอัปโหลดไม่ครบ ระบบแจ้งเตือนและยังเก็บข้อมูลการตรวจ/ปัญหาที่บันทึกสำเร็จไว้
7. **Maintenance Efficiency กับ Availability:** คงการแสดงสองความหมายจากต้นฉบับ ไม่สลับสูตรธุรกิจที่เคยเลือกไว้ ต้องอ่านชื่อและฐานคำนวณประกอบ

## ก่อนใช้งานเวอร์ชันนี้

อัปโหลดโค้ดชุดใหม่เข้า repository เดิม แล้วให้ GitHub Actions Build จาก lockfile หรือใช้ไฟล์ภายใน dist ทั้งชุด หลังเผยแพร่ให้ทดสอบหนึ่งงานจริงบนเครื่องและมือถือที่ใช้งานประจำ ตรวจว่าบันทึกผล/รูป/สถานะได้ตามสิทธิ์ของฐานเดิม รายงานนี้เป็นผลตรวจจากโค้ดและการทดสอบในสภาพแวดล้อมแยก ยังไม่ได้เผยแพร่เว็บแทนเวอร์ชันปัจจุบัน
